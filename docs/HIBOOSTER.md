# 当前 BL616 示例的 HiBooster UDP 协议

本文用于本仓库客户端实现，不是厂商发布的完整协议规范。
依据 BouffaloSDK `image_transmission` 示例和其静态库发送端、接收端实现核对：

```text
components/soln_utils/hibooster/lib/libhibooster_bl616.a
SHA-256: df3071faceccef4caf8dd2dbd94f3f74d330b019406f586eec7b93dd986072d6
```

升级 SDK / 静态库后应重新核对，不能直接假定其他芯片或库版本兼容。
所有多字节整数为小端；每个下列报文对应一个 UDP datagram。
本协议没有应用层加密或认证，Wi-Fi 链路安全取决于板端网络配置。

## 会话控制

| 操作 | 完整十六进制负载 |
| --- | --- |
| START | `EF 00 04 00` |
| STOP | `EF 01 04 00` |

原 SDK 板端监听 UDP 8800，并向 START 的源地址、源端口发送图像。
客户端使用同一个 socket 发送 START/STOP/ACK 和接收图像。
示例：手机 `9000 → 板端 8800`，图像 `板端 8800 → 手机 9000`。
当前测试板默认配置为手机 `1235 → 板端 8801`，图像目标为手机 `1235`。
接收端使用未 connect 的 UDP socket，只接受所填设备 IP 的数据，不限定图像的来源端口；
START、STOP、ACK 仍发往配置的板端指令端口，界面显示实际收到数据的来源 IP/端口。

本实现开启前先发送 STOP，等待 150 ms，再每 100 ms 重试 START，
直至收到发送 START 后的有效分片，允许首个帧序号大于 1。收到后停止重试 START，避免重新触发 sender。
5 秒未收到完整帧，或正在播放时 3 秒没有完整帧，会请求 STOP 并回到就绪状态。
这些超时是客户端策略，不是协议字段。
原始 UDP 数据报数和字节数在协议校验前累计，首包保留前 64 字节用于核对协议；
开启超时会区分无 UDP 数据、收到数据但协议不符，以及收到分片但未收齐帧。

关闭时发送三次 STOP，然后清理本地画面和重组状态。STOP 没有应答；UDP 可能丢包。
协议没有会话随机数，客户端本地 generation 可以屏蔽旧解码任务，无法识别所有网络迟到包。

## 图像分片：56 字节头 + JPEG 片段

| 偏移 | 字节数 | 含义 |
| --- | --- | --- |
| 0 | 1 | `93` |
| 1 | 1 | 图像类型 `01` |
| 2 | 2 | 整个 UDP 负载长度，包括 56 字节头 |
| 4 | 4 | 当前库格式字段：`02 02 00 01` |
| 8 | 8 | 帧序号，从 1 开始 |
| 16 | 16 | 本客户端不解释的字段 |
| 32 | 4 | 片段索引，从 0 开始 |
| 36 | 4 | 该帧片段总数 |
| 40 | 4 | 完整 JPEG 的字节数 |
| 44 | 2 | 图像宽度 |
| 46 | 2 | 图像高度 |
| 48 | 1 | JPEG quality |
| 49 | 7 | 保留/诊断字段，不参与重组 |
| 56 | 可变 | JPEG 分片，非末片为 1024 字节 |

重组位置为 `片段索引 × 1024`，总片数须等于 `ceil(JPEG 字节数 / 1024)`。
校验长度、元数据一致性及范围后，按位图防止重复写入。
收齐一帧后发送完成 ACK，再将 JPEG 交给 ImageIO 解码。

客户端最多保留 4 帧，单帧上限 512 KiB / 512 片；不完整帧超过 500 ms 即放弃。
完整帧释放 JPEG 缓冲后仍保留完成状态，收到重传包时再次 ACK，避免重复显示和重新分配。
较旧帧被淘汰后不重新建立缓存。

## ACK：32 字节总头 + 一个或多个 ACK item

本客户端每个 ACK datagram 只携带一个 item。

| 偏移 | 字节数 | 含义 |
| --- | --- | --- |
| 0 | 1 | `EF` |
| 1 | 1 | ACK 类型 `02` |
| 2 | 2 | UDP 负载总长度 |
| 4 | 4 | `02 02 00 01` |
| 8 | 1 | item 数量，本实现为 1 |
| 9 | 23 | 本实现置零；不使用控制透传字段 |
| 32 | 可变 | ACK item |

每个 item：

| item 内偏移 | 字节数 | 含义 |
| --- | --- | --- |
| 0 | 8 | 帧序号 |
| 8 | 4 | 状态：0 部分收到、1 收齐、2 放弃 |
| 12 | 4 | item 长度，包含此 16 字节头 |
| 16 | 可变 | 仅状态 0 携带接收位图 |

部分 ACK 位图长度为 `ceil(片段数 / 8)`，片段 i 对应
`bitmap[i / 8] & (1 << (i % 8))`，1 表示已收到。收齐/放弃的 item 长度为 16，
因此只有一个完成 item 的 ACK 总长度为 48 字节。
收齐时立即发送完成 ACK。首片到达后先留出 20 ms 收包窗口，窗口结束时仍缺片才在下一次定时检查发送位图。
仍缺片时每 20 ms 检查是否需要补发位图。收到已结束帧的重传时按帧合并补发 ACK。
若 80 ms 内未见下一帧分片，只补发最新帧的 ACK，收到更新帧后停止补发旧帧。

当前未实现 HiBooster 控制透传或升级消息；小汽车操控板透传需另行确认协议后开发。
